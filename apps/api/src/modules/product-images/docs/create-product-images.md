Метод `create()` спочатку **завантажує три файли в R2**, а потім **зберігає їхні URL і метадані в PostgreSQL**. Якщо виникає помилка — перевіряє, чи потрібно прибрати завантажені файли.

Ключовий момент: **транзакція Prisma охоплює тільки БД**. Вона не може автоматично скасувати завантаження в R2 — для цього потрібен `cleanupUpload()`.

**Як працює `create()`**

1. **Перевіряє власника зображення.**

   ```ts
   const variantId = data.variantId ?? null;
   await this.assertOwnerExists(productId, variantId);
   ```

   Продукт має існувати. Якщо передали `variantId`, перевіряється також, що цей варіант належить продукту. `null` означає спільне зображення продукту.

2. **Готує три WebP-файли через Sharp.**

   ```ts
   const derivatives = await this.imageProcessor.process(file);
   ```

   Результат містить `thumbnail`, `medium`, `large`: для кожного — `buffer`, ширину й висоту.

3. **Створює ідентифікатор зображення та ключі для R2.**

   ```text
   products/{productId}/{imageId}/thumbnail.webp
   products/{productId}/{imageId}/medium.webp
   products/{productId}/{imageId}/large.webp
   ```

   Це ключі об’єктів усередині bucket. Один `imageId` об’єднує три версії одного зображення.

4. **Послідовно завантажує файли в R2.**

   ```ts
   await this.storage.putObject({
     key: keys[name],
     body: derivatives[name].buffer,
     contentType: 'image/webp',
     cacheControl: 'public, max-age=31536000, immutable',
   });
   ```

   Через dependency injection `this.storage` — це `R2StorageService`. Усередині він виконує `S3Client.send(new PutObjectCommand(...))`: передає bucket, ключ і байти файлу до R2.

   `cacheControl` дозволяє кешувати файл на рік. UUID у ключі дає кожному новому зображенню окрему адресу.

   Послідовність спрощує прибирання після помилки: наступний upload не стартує, поки попередній не завершився.

5. **Після upload відкриває транзакцію БД.**

   Усередині вона:

   - бере lock на продукт;
   - перевіряє, чи не минуло 5 хвилин від підготовки ключів;
   - повторно перевіряє продукт і варіант: їх могли видалити, поки працювали Sharp і R2;
   - якщо `isPrimary: true`, знімає цей прапорець із попереднього головного зображення **для тієї самої пари `productId + variantId`**;
   - створює запис `ProductImage`.

   У БД потрапляють URL трьох файлів, `storageKeyBase`, зв’язки з продуктом/варіантом, розміри `large`, `alt`, `sortOrder`, `isPrimary`.

   `getPublicUrl()` лише складає адресу:

   ```ts
   `${R2_PUBLIC_BASE_URL}/${key}`
   ```

   Він нічого не завантажує.

**Що робить `lockImageProduct()`**

У [image-storage.utils.ts](/home/svash/my-work/monorepo/market-cosmo/apps/api/src/modules/product-images/image-storage.utils.ts:5) це SQL-запит:

```sql
SELECT "id"
FROM "Product"
WHERE "id" = $1
FOR UPDATE;
```

Він **блокує рядок конкретного продукту до завершення транзакції**. Інша транзакція, яка хоче взяти такий самий lock, чекатиме. Звичайне читання продукту це не блокує.

Приклад: два запити одночасно додають головне зображення одного варіанта.

- Запит A бере lock, прибирає старий `isPrimary`, створює своє головне зображення й завершує транзакцію.
- Запит B чекає, потім бере lock, бачить результат A, знімає з нього `isPrimary` і створює своє.

Так операції виконуються по черзі. Блокують саме **продукт**, бо рядок продукту вже існує навіть тоді, коли зображень ще немає.

Це працює між різними інстансами API, бо lock зберігає PostgreSQL. Ціна такого рішення — зміни зображень різних варіантів одного продукту також чекатимуть одна одну. Обробка Sharp і upload виконуються до lock, тому не тримають його під час повільних операцій.

**Навіщо `cleanupUpload()`**

Припустімо, `thumbnail` уже завантажився, а upload `medium` завершився помилкою. Запису `ProductImage` немає, але в R2 залишився файл. `cleanupUpload()` організовує його видалення.

Проте **помилка від БД не завжди означає, що commit не відбувся**: PostgreSQL міг зберегти запис, а з’єднання обірвалося до отримання відповіді. Тому helper діє обережно:

1. Відкриває нову транзакцію й бере той самий lock, очікуючи завершення попередньої операції.
2. Шукає `ProductImage` за `imageId`.
3. **Якщо запис існує — файли залишає.**
4. Якщо запису немає — створює `ImageCleanupTask` для всіх трьох ключів.
5. Викликає `cleanup.drain()`, який пробує видалити об’єкти з R2 та прибирає успішно виконані задачі з БД.

Перевіряються всі ключі, бо навіть upload, який повернув помилку, міг фактично зберегти файл.

При невдалому видаленні задача залишається для повторної обробки. Якщо сама БД недоступна, helper лише логує проблему й зберігає файли: результат commit невідомий. Для подальшого прибирання є recovery-механізм `images:recover`; цей метод сам не запускає фоновий таймер.

Отже, `lockImageProduct()` узгоджує конкурентні зміни в БД, а `cleanupUpload()` компенсує невдалу операцію між двома окремими системами — PostgreSQL і R2.
