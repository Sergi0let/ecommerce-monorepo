Окремий `StorageModule` потрібен, щоб **бізнес-логіка працювала з файлами, не залежачи від деталей Cloudflare R2**.

`ProductImagesService` вирішує, кому належить фото, чи воно головне і що записати в БД. `StorageModule` відповідає за доставку байтів у сховище, видалення об’єктів та отримання інформації про них.

**Як розділено код**

```text
common/
├── images/
│   └── image-processor.service.ts  # Sharp: resize, WebP
└── storage/
    ├── object-storage.interface.ts # Контракт операцій зі сховищем
    ├── r2-storage.config.ts        # Завантаження і валідація конфігурації
    ├── r2-storage.service.ts       # Реалізація операцій для R2
    └── storage.module.ts           # Створення та підключення залежностей

modules/product-images/
├── product-images.service.ts       # Правила галереї та записи в БД
├── image-cleanup.service.ts         # Прибирання файлів після видалень/помилок
└── image-recovery.service.ts        # Відновлення узгодженості БД і сховища
```

Storage не знає, що таке `isPrimary`, `ProductVariant` або транзакція Prisma. Він отримує ключ і байти файлу.

**Як NestJS підключає storage**

У [object-storage.interface.ts](/home/svash/my-work/monorepo/market-cosmo/apps/api/src/common/storage/object-storage.interface.ts) описаний контракт `ObjectStorage`:

- `putObject()` — зберегти файл;
- `deleteObject()` — видалити;
- `getPublicUrl()` — сформувати публічну адресу;
- `headObject()` — перевірити об’єкт і отримати дату зміни;
- `listObjects()` — перелічити об’єкти, зокрема для recovery.

Сервіс зображень отримує цю залежність:

```ts
@Inject(OBJECT_STORAGE)
private readonly storage: ObjectStorage
```

Тут дві різні речі:

- **`ObjectStorage`** — TypeScript interface: перевіряє типи під час розробки, але зникає після компіляції.
- **`OBJECT_STORAGE`** — runtime token: за ним NestJS знаходить потрібний об’єкт.

У [storage.module.ts](/home/svash/my-work/monorepo/market-cosmo/apps/api/src/common/storage/storage.module.ts) задане зіставлення:

```ts
{ provide: OBJECT_STORAGE, useExisting: R2StorageService }
```

Тобто: «коли просять `OBJECT_STORAGE`, передай наявний екземпляр `R2StorageService`».

Під час запуску модуль перевіряє конфігурацію, створює `S3Client` із R2 endpoint і credentials, а потім передає його в `R2StorageService`. Назовні експортує лише `OBJECT_STORAGE`.

Далі виклик проходить так:

```text
ProductImagesService
  → storage.putObject({ key, body, ... })
  → R2StorageService
  → S3Client / PutObjectCommand
  → R2 bucket
```

**Чому краще, ніж писати R2-код у кожному модулі**

Якщо записувати upload безпосередньо в модулях продуктів, аватарів і банерів, кожному доведеться працювати з SDK, конфігурацією, помилками та timeout-ами.

В окремому модулі:

- **Єдина поведінка.** Перевірка ключів, timeout-и, retries і перетворення помилок налаштовані централізовано.
- **Менше дублювання.** Новий модуль використовує `storage.putObject()`.
- **Простіше тестування.** У тестах бізнес-логіки можна підмінити `OBJECT_STORAGE` тестовою реалізацією без мережі та R2 credentials.
- **Простіша заміна провайдера.** Залежність від конкретного SDK зосереджена в адаптері.
- **Credentials залишаються в інфраструктурному шарі.** Сервісу продуктів не потрібні ключі доступу.

Це практичне застосування Dependency Inversion: бізнес-сервіс залежить від контракту, а конкретну реалізацію обирає конфігурація NestJS.

Додаткова ціна — interface і DI-конфігурація. Для вашого проєкту вони виправдані: storage уже використовують upload, cleanup і recovery.

**Як додавати нові можливості**

Наприклад, для аватарів новий сервіс може використовувати той самий storage з ключами `avatars/{userId}/{imageId}.webp`. Правила аватарів і їх обробка залишаються у відповідному модулі.

Якщо з’явиться нова операція сховища, її можна додати в контракт і реалізації. Але не варто заздалегідь додавати всі можливості SDK: контракт має відображати реальні потреби застосунку.

Сам `StorageModule` — **частина процесу NestJS, а не окремий мікросервіс**. Він не потребує додаткового контейнера. Кілька інстансів API можуть використовувати спільне зовнішнє сховище; водночас модуль сам не обмежує загальну кількість upload-ів між інстансами.

**Що зміниться при переїзді з R2**

Для нового провайдера створюємо, наприклад, `S3StorageService`, який реалізує `ObjectStorage`, додаємо його конфігурацію та змінюємо provider:

```ts
// Після реалізації та реєстрації S3StorageService:
{ provide: OBJECT_STORAGE, useExisting: S3StorageService }
```

Якщо збережена поведінка контракту, `ProductImagesService`, cleanup і recovery продовжать викликати ті самі методи.

Але **заміна адаптера не переносить існуючі файли та URL**. Для реального переїзду потрібно:

1. Скопіювати об’єкти в нове сховище зі збереженням ключів.
2. Перевірити доступність і цілісність файлів.
3. Узгодити перемикання нових upload-ів і pending cleanup-задач.
4. Перемкнути публічний домен або оновити збережені URL у БД.
5. Залишити старе сховище на період перевірки й можливого rollback.

Власний домен на кшталт `images.example.com` спрощує переїзд: якщо адреси й шляхи зберігаються, URL у БД можна залишити незмінними, переналаштувавши видачу файлів.

Є й поточні обмеження: контракт орієнтований на **публічні файли**, а cleanup-задачі не містять ідентифікатора сховища. Для приватних файлів із тимчасовими URL або одночасної роботи двох провайдерів контракт і модель даних доведеться розширити.

Перед перемиканням важливі інтеграційні перевірки нового адаптера: upload → читання, listing із pagination, видалення та поведінка для відсутнього об’єкта. TypeScript перевірить сигнатури, але не гарантує однакової поведінки сховищ.
